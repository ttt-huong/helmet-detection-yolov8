# Hardhat-only API contract audit (2026-11-28)

> **Historical source snapshot:** this audit inspected the earlier v8 API contract and its then-current `/predict` implementation. Later source revisions use the v9 release contract with per-subtype locked-test gate fields. The schema distinction below still applies, but the old gate/version and 7860 availability references are not current. No checkpoint or passing model test is established.

## Finding

Static code and rubric review confirms the intended **output schema**: model class 0 is `hard_hat_worn`; class 1 is auxiliary `depiction_region`. `traffic_helmet_worn`, `cap_worn`, and `beanie_worn` are review/negative-source names, not API class names or YOLO output labels ([rubric](../../configs/helmet_types_labeling.md#L5), [service class map](../../service/app.py#L22), [converter class map](../../scripts/convert_review_json_to_yolo.py#L51)). The rubric describes those non-target types as negative examples, and the release summary requires minimum independent-group counts for those sources ([rubric](../../configs/helmet_types_labeling.md#L14), [service sufficiency constants](../../service/app.py#L58), [summary checks](../../service/app.py#L349)).

This schema does **not** prove semantic rejection of every traffic helmet, cap, or beanie. The API has no separate non-target detector classes or visual rule that recognizes those hats. A model false positive can still be returned as a `hard_hat_worn` candidate. The sample-count gates do not by themselves prove zero false positives for each hat subtype. A checkpoint and its locked-test results are needed to measure that behavior.

## Routes and output behavior

- `GET /livez` returns `{"status":"alive"}` when the ASGI process serves requests; it does not report model readiness ([app.py:591-595](../../service/app.py#L591)).
- `GET /health` calls model loading and checks CUDA. It returns `200`/`status="ready"` only after those checks; model or GPU errors return `503` with `status="model_not_loaded"`, an `error_code`, the two class names, the zero-count policy, and the depiction-filter policy ([app.py:597-632](../../service/app.py#L597)).
- `POST /predict` accepts a required uploaded `image` and `confidence` query parameter defaulting to `0.25`; confidence outside `0.01–0.90` returns `422`. Model-load/GPU failures return `503` before image processing. The route runs inference on GPU 0 at 640 pixels with a low internal confidence floor of `0.001`, then applies the caller’s threshold to visible worn-hat candidates ([app.py:635-663](../../service/app.py#L635)).
- Upload validation rejects empty bytes (`400`), uploads over 10 MiB (`413`), unsupported MIME or decoded format (`415`), images over 24 megapixels (`413`), and unreadable images (`400`). It accepts JPEG, PNG, and WebP, applies EXIF orientation, and converts to RGB/BGR for inference ([app.py:442-473](../../service/app.py#L442)).
- Detection extraction only maps class IDs 0 and 1 to the configured names, drops unknown IDs/non-finite coordinates/degenerate boxes, and clips boxes to image bounds ([app.py:527-549](../../service/app.py#L527)). Filtering uses the union of all detected depiction-region intersections: a candidate is suppressed if its center lies in a region or coverage is at least 50%; positive overlap below 50% becomes `uncertain`; zero overlap remains `unverified`. All three cases are uncounted ([app.py:505-524](../../service/app.py#L505), [app.py:552-588](../../service/app.py#L552)).
- The response contains `detections`, `raw_detections_for_review`, `suppressed_wearer_candidates`, `uncertain_wearer_candidates`, and `wearer_candidates_for_review`. It always returns `wearer_count: 0`, `review_required: true`, `review_reason: "scene_source_not_verified"`, and `source_status: "unverified"` ([app.py:665-715](../../service/app.py#L665)). Thus a candidate can be displayed for human review but is never represented as a confirmed wearer count.

## Model loading and verification limits

`load_model()` requires `MODEL_PATH` to name a real checkpoint, then validates its v8 release receipt and test summary, artifact hashes, release gates, sufficiency floors, recorded training runtime, and GPU availability. It loads only a detection checkpoint whose class order is exactly `{0: hard_hat_worn, 1: depiction_region}` ([app.py:172-230](../../service/app.py#L172), [app.py:237-386](../../service/app.py#L237), [app.py:389-439](../../service/app.py#L389)). Release checks include 300/1/100 train/validation/test boxes for each model class; required hard-negative group floors; 300/30/100 train/validation/test groups for traffic-helmet, cap, and beanie negatives; and passing poster/printed-photo/screen gates with zero false unverified candidates ([app.py:53-68](../../service/app.py#L53), [app.py:306-384](../../service/app.py#L306)). These are release prerequisites, not evidence that a particular checkpoint has passed.

The workspace has no `best.pt`, `deployment_release.json`, or `deployment_test_summary.json` in the repository search; the live-readiness record also reports no local release artifacts and no reachable service at `127.0.0.1:7860` ([live API readiness](live-api-readiness-2026-11-28.md#L9), [artifact check](live-api-readiness-2026-11-28.md#L20)). No route, checkpoint, detector accuracy, recall, or false-positive behavior was exercised in this audit. Findings above are static code/rubric claims only; deployment and model-level behavior remain unverified until the matching release artifacts are installed and the cloud GPU service passes `/health` and locked-test gates.
